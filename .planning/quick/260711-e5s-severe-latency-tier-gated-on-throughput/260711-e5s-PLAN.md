<objective>
Add a **severe-latency tier** to probe classification, gated on measured throughput.

**The bug this closes.** On-device today: a `.probeSuccess` event logged with **10011 ms** latency.
`isDropEvent()` returns false for `.probeSuccess` at ANY latency, so a ten-second probe counts as a
SUCCESS in the dashboard counts, the summary report, and the failure rate that goes to Apple. That
**undercounts the real failure rate**. It is also inconsistent with the app's own throughput model,
which already has both tiers: `.slowThroughput` (degraded, not a drop) and `.severeThroughput`
(a drop). Latency has only the degraded tier (`HealthScore.slowLatencyThresholdMs` = 3000).

**Why this is not just "add a latency threshold".** iOS exposes **no public signal-strength API** —
none, anywhere in the iOS 26 SDK. Private APIs (`CTGetSignalStrength`, status-bar scraping) are
**rejected**: this app's JSON export is evidence in an Apple engineering escalation, and a diagnostic
tool that reads undocumented internals hands Apple a free way to dismiss the entire dataset.
Consequence: a slow probe might legitimately be **weak signal** (expected physics on one bar in a
basement), not a modem defect. Blaming the modem for bad coverage would be dishonest and Apple would
rightly tear it apart.

**The rule (LOCKED — do not revisit, do not "improve").** Gate severe-latency on **throughput**, which
the app already measures and which is a genuine signal-quality proxy. Weak signal degrades latency AND
throughput together (physics). A modem stall gives bad latency with **healthy** throughput.

| latency | recent throughput reference | classification |
|---|---|---|
| > 5000 ms | healthy (>= 1 Mbps), fresh | **`.severeLatency` = DROP** — the radio was demonstrably capable; the modem stalled |
| > 5000 ms | poor (< 1 Mbps), fresh | stays degraded, **NOT a drop** — consistent with weak signal |
| > 5000 ms | absent OR stale | stays a success, **NOT a drop** — capability unproven, so no claim is made |
| <= 5000 ms | anything | clean success (unchanged) |

Purpose: stop undercounting the failure rate in the evidence that goes to Apple, without ever
attributing a coverage problem to the baseband.

Output: a pure, machine-tested classification rule; a new `.severeLatency` event type wired through
drop counts, chart, analytics and report; and a per-event record of the throughput reading that drove
each decision.
</objective>

<locked_decisions>
Settled by the user. Implement exactly; do not re-derive.

- **D-01** Severe latency is gated on throughput. No other gate, no other proxy.
- **D-02** Slow + healthy throughput -> DROP. Slow + poor throughput -> not a drop. Slow + no/stale
  data -> not a drop (conservative: cannot prove the radio was capable, so do not claim it).
- **D-03** `severeLatencyThresholdMs = 5000`. "Healthy throughput" = `>=` the existing
  `slowThroughputThresholdKbps` (1000 Kbps).
- **D-04** New `EventType` case `.severeLatency` with **explicit rawValue 12** (11 = `.dataStall` is
  the current highest; every case in this enum carries an explicit rawValue for migration safety).
- **D-05** The rule runs at **capture time**, on **cellular** probes only.
- **D-06** New field `referenceThroughputKbps: Double?` records the reading that drove the decision.
- **D-07** **No retroactive mutation.** The 100+ days of stored events are evidence and stay exactly
  as captured. The new rule applies to newly captured events only.
</locked_decisions>

**1. Create `CellGuard/Helpers/SevereLatencyRule.swift`.**

It must import **Foundation only** — no SwiftData, no SwiftUI, no `ConnectivityEvent`. That
dependency-freedom is load-bearing: it is exactly what lets the verify step compile this production
file standalone with `swiftc` and prove all four branches on a real machine run. This is the sole
reason the rule is extracted rather than inlined in `ConnectivityMonitor` (per D-02 the rule is pure
logic over latency + throughput + freshness, so extraction costs nothing and buys a real test).

```
enum SevereLatencyRule {
    static let severeLatencyThresholdMs: Double = 5000
    static func isSevere(
        latencyMs: Double?,
        referenceThroughputKbps: Double?,
        referenceAge: TimeInterval?,
        freshnessWindow: TimeInterval,
        healthyThroughputKbps: Double
    ) -> Bool
}
```

`healthyThroughputKbps` is a **parameter, not a constant** — the caller passes its existing
`slowThroughputThresholdKbps`, so the 1 Mbps healthy/degraded line stays a single number with a
single owner and cannot drift between the two classifiers.

Implementation is three guards, in this order:
  1. `latencyMs` present AND `> severeLatencyThresholdMs`, else false (fast probe, or a nil latency
     from an app-suspension artifact — both are "not severe").
  2. A reference throughput AND its age are present AND `age <= freshnessWindow`, else false
     (the NO-DATA branch: capability unproven, so make no claim).
  3. `referenceThroughputKbps >= healthyThroughputKbps` — the radio was demonstrably capable, so the
     slow probe is the modem stalling, not the coverage.

Doc-comment the WHY at the top of the type, because a future reader will otherwise "fix" the
conservative branches: iOS exposes no public signal-strength API and private ones are rejected
(the export is evidence in an Apple escalation); throughput is the honest proxy because weak signal
degrades latency and throughput *together*, while a modem stall degrades latency alone. State the
four branches from the objective table verbatim as the rule's contract.
