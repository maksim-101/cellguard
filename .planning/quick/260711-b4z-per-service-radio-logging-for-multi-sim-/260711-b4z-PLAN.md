<objective>
Fix a data-integrity bug and add per-service (multi-SIM / DSDS) radio logging so the secondary
eSIM's state can be correlated against the 317 logged silent failures.

**The bug.** `ConnectivityMonitor.swift` lines 295, 801 and 842 each read
`freshInfo.serviceCurrentRadioAccessTechnology?.values.first`. Swift's `Dictionary.values` has
NO defined ordering. With two SIM services present this samples an ARBITRARY line. Two
consequences, both corrupting:
  (a) `radioTechnology` on existing events may describe the WRONG line;
  (b) `.radioTechChange` fires on `oldTech != newTech`, so a mere dictionary-iteration-order flip
      between two services emits a PHANTOM radioTechChange that never physically happened.

**The hypothesis this feeds.** The Tello (US) eSIM cannot register on any Swiss network, so it
hunts continuously. In DSDS both lines share one RF chain, and PLMN search / paging / signalling
on the idle line outranks packet data on the active line. Recording both services' state at every
event is what makes that contention visible.

Purpose: the resulting JSON export is evidence in an Apple engineering escalation and possibly a
Swiss consumer-law claim. Data integrity is paramount — see the migration constraint below.

Output: deterministic primary-line selection, a per-service radio snapshot on every event, the
changed-service identifier on every radioTechChange, structured export, event-detail surfacing,
and an in-app self-check that settles the two on-device unknowns with one screenshot.
</objective>

<sdk_facts_already_verified>
These were checked against `iPhoneOS26.5.sdk/.../CoreTelephony.framework/Headers/CTTelephonyNetworkInfo.h`
during planning. **Do not re-litigate them; do not add fallback scaffolding for them.**

1. **`CTTelephonyNetworkInfo.dataServiceIdentifier` EXISTS and is NOT deprecated.**
   `@property(readonly, copy, nullable) NSString *dataServiceIdentifier API_AVAILABLE(ios(13.0))`
   — "An NSString representing the identifier of the service that's currently providing data."
   It is **nullable**, so a deterministic fallback is still required for the nil case. Its runtime
   behavior on a live dual-eSIM device remains an on-device unknown (Task 3).

2. **The notification's `object` IS the service identifier.** Header doc for
   `CTServiceRadioAccessTechnologyDidChangeNotification`: "Only an object is sent with this
   notification. The object is an NSString that represents the service identifier of the service
   whose radio access technology has changed. This NSString should be used as the key in
   serviceCurrentRadioAccessTechnology…" This is exactly what line ~798 currently throws away.

3. **`serviceSubscriberCellularProviders` still compiles on iOS 26** — `API_DEPRECATED("Deprecated
   with no replacement", ios(12.0, 16.0))`. Deprecated, present in the SDK. Its CTCarrier VALUES are
   junk post-16.4 and must never be read; only its KEYS are used. **The resulting deprecation warning
   is expected and accepted — do not add suppression scaffolding for it.** Whether it still returns
   keys at runtime on iOS 26 is on-device unknown #2 (Task 3).

4. **Absence semantics are documented by Apple.** `serviceCurrentRadioAccessTechnology` doc: "An
   entry may be nil if the service is not registered on any network." An unregistered line is
   therefore an ABSENT KEY. That absence is the signal we are hunting.

5. **The project uses `PBXFileSystemSynchronizedRootGroup`** — a new `.swift` file under `CellGuard/`
   is picked up automatically. **Do not touch `CellGuard.xcodeproj/project.pbxproj`** (it already
   carries an unrelated uncommitted modification; leave it alone).
</sdk_facts_already_verified>

<migration_constraint priority="highest">
The device store holds 100+ days of irreplaceable evidence. A migration crash destroys the Apple case.

- **Every new property MUST be optional (`String?`) with a nil default.** SwiftData backfills a new
  *optional* attribute with nil and needs no declaration default — this is the path already proven
  in this store by `vpnInterface: String?` and `throughputKbps: Double?`.
- **If you add ANY non-optional property you MUST give it `= default` ON THE PROPERTY DECLARATION**
  (not just in `init`). SwiftData reads the *declaration* default to backfill existing rows; without
  it, launch crashes with CoreData error 134110. See the `lowPowerMode` and `pathUsesCellular`
  comments in `ConnectivityEvent.swift` — they exist because this already bit this project once.
- **Prefer one optional String holding a compact encoded map over one column per service.** The
  service count is device-dependent; columns are not.
</migration_constraint>

  - `service: String` — the opaque CoreTelephony service identifier (e.g. "0000000100000001").
  - `tech: String?` — the radio access technology this service is registered on, e.g.

    Use a `JSONEncoder` with `.sortedKeys` output formatting so the stored string is deterministic

    an empty array** — no cellular services means no data, not an empty JSON array.
