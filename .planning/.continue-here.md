# BLOCKING CONSTRAINTS — Read Before Anything Else

> Each of these was discovered through actual failure this session. Acknowledge each before proceeding.

- [ ] **CONSTRAINT: The SwiftData store is irreplaceable evidence.** 100+ days of event data back a live Apple engineering escalation and a possible Swiss consumer-law claim. A migration crash (CoreData **134110**) destroys the case. **Structural mitigation:** every new `@Model` property MUST be optional (`String?` / `Double?`). A non-optional needs `= default` on the **property declaration** (not merely in `init`) — SwiftData reads the declaration default to backfill existing rows. Precedent comments live in `ConnectivityEvent.swift` on `lowPowerMode` / `pathUsesCellular`. Every schema change gets a migration smoke test against a **copy of a populated store** before it is called done.

- [ ] **CONSTRAINT: Never claim runtime behaviour works from code reading.** The iOS Simulator has **no cellular interface**, so it can exercise neither dual-SIM CoreTelephony nor throughput measurement. Anything touching those is **"built, not yet verified"** until the physical iPhone 17 Pro Max says otherwise. **Structural mitigation:** every such task carries a blocking human-verify checkpoint, and the SUMMARY separates machine-verified from device-pending. Do not blur that line.

- [ ] **CONSTRAINT: No private APIs, ever, for signal strength.** `CTGetSignalStrength` and status-bar scraping would *work* on a sideloaded build — and would hand Apple a free way to dismiss the entire dataset ("your tool reads undocumented internals"). **There is no public signal-strength API on iOS. Stop looking.** Throughput is the only permitted signal-quality proxy — which is precisely why `.severeLatency` is gated on it.

- [ ] **CONSTRAINT: Never retroactively mutate stored events.** They are evidence. Historical events lack `referenceThroughputKbps` and therefore *cannot* be honestly reclassified. That is correct and intended, not a gap to fix. Do not write a migration that rewrites `eventTypeRaw`.

**Do not proceed until all boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---|---|---|---|
| Non-deterministic dictionary sampling | `serviceCurrentRadioAccessTechnology?.values.first` — `Dictionary.values` has **no defined ordering**. With two SIM services present, the app sampled an *arbitrary* line for months, corrupting `radioTechnology` and emitting phantom `radioTechChange` events. | blocking | Always key CoreTelephony dictionaries by an explicit service identifier. `captureRadioSnapshot()` now resolves the primary via `dataServiceIdentifier` with a **sorted-key** fallback (arbitrary but *stable*, so the tie-break can never manufacture a transition). |
| Reclassifying an event type without re-wiring the counters | Moving a slow probe out of `.probeSuccess` **removes it from `HealthScore.probeOutcomeTypes`** (the denominator) and therefore *raises* the health score — inverting the very fix. | blocking | Any new drop-type `EventType` must be added to `probeOutcomeTypes`, `isDropEvent()`, `DropTimelineChart`, and `AnalyticsView` in the same change. Verified by the plan-checker against live code. |
| Importing a workaround without checking its mechanism | Claude recommended "turn on Wi-Fi Calling so the line stops hunting." The user correctly refuted it: with no Wi-Fi in range — i.e. **exactly when the problem occurs** — the line still has to hunt. The community workaround's causal roles had been mis-assigned. | advisory | State the mechanism before recommending the remedy. Correct model: **manual network selection stops the hunt**; Wi-Fi Calling is only a reachability *backstop* afterwards. |
| Fabricated statistics from research agents | A prior research agent invented event counts and stall durations as if from the user's own data. | blocking | **Never invent numbers.** Only use figures traceable to a real CellGuard export or a screenshot. Mark anything unknown as an explicit placeholder. |

<decisions_made>

- **Severe-latency reclassification is gated on measured throughput, not latency alone.** iOS exposes no signal strength, so a slow probe *could* be honest weak-signal physics. Weak signal degrades latency **and** throughput together; a modem stall gives bad latency with *healthy* throughput. Four branches: slow+healthy → DROP; slow+poor → not a drop; slow+no-or-stale data → not a drop (conservative); fast → clean.

<context>
**Root cause — settled. Do not re-litigate it.**

The second eSIM (Tello, a US voice-only line) cannot register on any Swiss network, so it searches continuously. The iPhone is **DSDS** — both lines share **one RF chain** — and paging, signalling and network-search on the *idle* line take **priority over packet data** on the active line. So the Swisscom line reports full bars and 5G while passing **zero data for hours**, and iOS never detects it.

**Apple's own telemetry confirms it.** Settings → Battery → "Poor Cell Coverage" reads **~zero on exactly the two days Tello was off** (Wed 7/8 and Fri 7/10 — dates *verified*) and 1.5–3.5% on every other day. This proves the idle line is actively burning radio rather than sitting dormant, and it comes from iOS itself — Apple cannot dismiss it as third-party instrumentation. It is the strongest single artefact in the case.

**Dead hypotheses — do not revive:**
- *Region locale.* The user set the region back to US and the issue did **not** return on that account. The 2026-07-08 conclusion that "region=CH is the fix" was **wrong**.
- *5G SA hunting.* The failure occurs with the second line on **5G *and* on LTE**, so RAT preference is not the variable. It's the network search itself.

**Unexplained, worth chasing:** all three multi-hour "zombie modem" events start at **04:49 / 04:55 / 05:09** — the same time of day. A ~24-hour retry timer (3GPP **T3245**, the forbidden-PLMN retry timer, max 24 h) would produce exactly that. Give it to Apple as a hypothesis for *them* to test, never as a conclusion.
</context>
